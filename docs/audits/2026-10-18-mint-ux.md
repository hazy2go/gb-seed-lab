# Mint page and mint process audit (2026-10-18)

Scope: `web/index.html`, `web/mint.js`, `web/mint.css`, `server/src/index.mjs` (+ gallery, solana, storage, lanes), from the buyer's side. Read-only: no project file changed except this report and its images.

How it was tested
- `server/scripts/demo.mjs 8795` (the existing demo) at 1440x900, 1280x800, 1920x1080, iPhone 15 Pro 393x852 and Android 360x780, headless Chrome via puppeteer-core.
- A scratch copy of the demo with state controls (offline/online, closed/open, sold out, abort, pause, seeding-only queue, 2000 in line, failing submit, collector pieces + refunds) and a fake Wallet Standard wallet that signs with a real keypair, so the page's buy flow ran end to end (ticket, checkPayment, sign, submit, queued, seeded). No chain, nothing deployed.
- Read-only GETs on the live API: `api.gameboylabs.xyz/api/health` and `/api/state` (mainnet, `closed: true`, lane offline, sold 0). The live `www.gameboylabs.xyz/slow-horizons/` HTML and mint.js are identical to the repo.
- Line numbers are from the files as of commit time of this audit (mint.js 664 lines, index.mjs 527 lines).

Images: `docs/audits/img/mint-ux/`.

## Critical

### C1. One payment can become two pieces (race in handlePayment)
- **Where:** `server/src/index.mjs:70-101` (check `usedSignatures`, then `await sol.inspectPayment`, then record) and `:445` (the /api/submit background loop calls `handlePayment` every 5 s) while `poll()` (`:106-126`, every 8 s) calls it for the same signature.
- **What:** there is no in-flight guard. When the watcher and the submit loop both reach a freshly finalized signature within one RPC round trip, both pass the `usedSignatures` check and both create a piece (two numbers, two draws, two mints, `sold` counts 2). The same applies to refund records (double "refund due").
- **Repro (logic copy, scratch `race.mjs`):** same three steps as `handlePayment` with a 300 ms RPC; second call starts 120 ms later: `pieces for one payment: [ 1, 2 ]`. In production the overlap window is roughly RPC latency / 5 s + latency / 8 s, i.e. a few percent of payments made through the page.
- **Fix:** keep a `Map<signature, Promise>` of in-flight checks and return the existing promise; or re-check `state.usedSignatures[signature]` right after the `await` and before creating the piece (synchronous section, so it is atomic in Node). Add a test that fires two concurrent `handlePayment(sig)`.

### C2. Page breaks when the first entry in line is still waiting for its seed
- **Where:** `web/mint.js:262` calls `renderLabel(live.piece || snap?.queue?.[0])`; `renderLabel` (`:104-107`) reads `p.traits.palette`, but a `seeding` piece has `traits: null` (`index.mjs:93`, `publicPiece :338`).
- **What:** whenever nothing is drawing and the oldest piece in line is still seeding (the first purchase after an idle studio, which is exactly launch time, and every new visitor or reconnect during that ~15-30 s window) `renderAll` throws on its third call. Price, queue, wall, buy button never render: the page says "Studio open, the Game Boy is waiting for a commission" next to a disabled **"Studio offline"** button, no price, "Nobody in line" although someone is.
- **Repro:** demo copy with one seeding piece, no drawing; open the page. Console: `Cannot read properties of null (reading 'palette')`.
- **Evidence:** `06-seeding-first-crash.jpg`.
- **Why the demo never showed it:** `demo.mjs:34-38` gives seeding pieces a seed and traits, unlike the real server.
- **Fix:** in `renderAll` pick `live.piece || snap.queue.find(p => p.traits)`, and make `renderLabel` handle `!p.traits` ("No. N, paid, seed coming"). Wrap each render step so one failure cannot blank the rest. Make the demo's seeding pieces `seed: null, traits: null` like the server.

### C3. After paying, the buy button re-arms in 4 s and nothing durable says "you paid"
- **Where:** `web/mint.js:427-429` (`finally { setTimeout(() => { busy = false; renderBuy(); }, 4000) }`), `:295-300` (button text set once, overwritten by the next `renderAll`), `:422` (note), `:313-318` (`bump` drops `seeding` pieces, see H5).
- **What:** timeline measured with the fake wallet (finalization simulated at 15 s, seed at 28 s): 0.5 s "Paid. Waiting for the network…", **4.2 s "Commission a piece for 0.05 SOL" (enabled)**, 15.2 s "Paid. You are No. 575." for 1.5 s, then back to "Commission a piece…". The "Your place in line" card only appears at 28 s (after the seed). On mainnet the gap is 15-45 s. A buyer who looks up from the wallet sees a fresh buy button and an unchanged queue and pays again. Reloading in that window shows nothing at all (no local record, `waitingFor` is in memory).
- **Evidence:** `08-buy-sign-3s.jpg`, `08-buy-sign-10s.jpg` (button live again, only the small grey note hints at a payment).
- **Fix:** a persistent "pending payment" card (signature, explorer link, "waiting for the network, then your number") that stays until the piece or a refund for that signature appears; store `{signature, wallet, at}` in localStorage and restore it on load; keep the button disabled or relabel it "Commission another piece" with a confirm while a payment of this wallet is pending; let the server answer `GET /api/payment?sig=` (pending / piece N / refund) so the page can poll instead of relying on WebSocket events.

## High

### H1. Network rejections are shown as "You cancelled in the wallet. Nothing was paid."
- **Where:** `web/mint.js:425` regex `/reject|cancel|declin/i`; the server's own text is "The network rejected the transaction: …" (`index.mjs:442`).
- **What:** expired blockhash (buyer took > ~60-90 s in the wallet, common on phones), insufficient SOL, any preflight failure all match "rejected" and the buyer is told they cancelled. A Wallet Standard rejection without those words shows the raw error ("WalletSignTransactionError").
- **Repro:** demo copy with `/api/submit` returning "The network rejected the transaction: Transaction simulation failed: Blockhash not found" (and "…no record of a prior credit"). Toast: "You cancelled in the wallet. Nothing was paid."
- **Fix:** classify by stage, not text: errors thrown by `provider.signTransaction` with `code === 4001` or a rejection name are cancels; errors from `/api/submit` are network errors. Map known cases: blockhash expired -> "The payment took too long to approve and expired. Nothing was paid. Try again."; insufficient funds -> "Not enough SOL: you need 0.05 SOL plus a small network fee." Better: have `/api/ticket` check the wallet balance (server has the RPC) and refuse with that message before the wallet opens; fetch the ticket right before signing or rebuild on expiry.

### H2. Open/closed, sold count and sold out go stale after page load
- **Where:** `mintOpen`, `mintClosedReason`, `sold`, `secondsPerPiece` only arrive in the snapshot (`index.mjs:351-361`), which is sent on connect and on /admin/open|close only (`:474-475`). Lane changes send `{type:'lane'}` (`:152-153`), and the page only copies `snap.lane` (`mint.js:302`). `renderBuy` (`:250-261`) and `renderPrice` (`:241-249`) read the stale fields.
- **What:**
  - Game Boy goes offline while a tab is open: status says "Studio closed: the Game Boy is not connected", the buy button stays **enabled** (`10-offline-live.jpg`); clicking it gets a 503 toast.
  - Tab opened while offline, Game Boy comes back: status "Drawing No. 413", button stays **"Closed while the Game Boy is offline"** until reload (`13-online-but-button-closed.jpg`). Every tab open during a lane blip stays unable to buy.
  - "675 of 2000 taken" stayed frozen for 36 s while the server went to 680 (measured). The meter never moves; sold out is never shown live; "payment watcher behind" never clears.
- **Fix:** broadcast a small `{type:'mint', mintOpen, mintClosedReason, sold, secondsPerPiece}` whenever any of them changes (lane ready/down, payment recorded, pause/resume, poll age crossing 120 s), or include them in every `lane`/`queued`/`status` message. In `bump()` also update `snap.sold` for new pieces.

### H3. A drawing that is aborted stays "Drawing No. N" on every open page
- **Where:** server `abort()` (`index.mjs:207-217`) and the mismatch path (`:228-234`) only broadcast `status: queued` / `lane`; the page clears `live` only on `drawn` (`mint.js:290`) or a new snapshot (`:273-274`).
- **What:** Game Boy dies or stalls (150 s watchdog), restarts mid-drawing, or the tiles mismatch: the studio keeps "LIVE · seed", "Drawing No. 413 on the Game Boy, ridge done", and the foot counts up to "about 0:00 to go" forever (measured 31 s after abort, unchanged; `09-abort-stuck-drawing.jpg`). After a mismatch on phase 8 it reads "…done done". No page ever learns why. The collector whose piece it was is not told it will be redrawn.
- **Fix:** broadcast `{type:'aborted', n, reason, willRetry}`; on the page reset `live`, show the reason in the studio foot ("The Game Boy stopped answering. No. 413 goes back to the front of the line and is redrawn from the start; nothing is lost.") and a toast to the owner wallet. Also send `drawing` state in `lane` messages so a client can self-correct.

### H4. When drawing is paused, the page keeps selling and says the studio is waiting
- **Where:** `mintOpen()` (`index.mjs:62-68`) ignores `lanePaused` (set after 3 faults in a row or any mismatch, `:215`, `:230`, cleared only by `/admin/resume`). `renderStatus` (`mint.js:143-152`) ignores `snap.lane.paused`.
- **What:** with drawing paused (needs Hazy), a fresh tab shows "Studio open, the Game Boy is waiting for a commission", buy enabled, queue ETAs "in ~3 min". Buyers pay into a line that does not move, possibly for hours overnight.
- **Fix:** `mintOpen` returns `{open:false, reason:'paused'}` when `lanePaused`; page text "Paused: the Game Boy needs a check. Paid pieces keep their place and are drawn when it resumes." Queue ETAs show "paused" instead of minutes.

### H5. New payments are missing from the line until their seed, and refunds never show live
- **Where:** `bump()` (`mint.js:313-318`) keeps only `queued|drawing`; the server announces a new piece as `{type:'queued', piece:{status:'seeding'}}` (`index.mjs:99`). The snapshot includes seeding pieces (`:352`), events do not.
- **What:** live tabs never show "Getting its seed" rows (measured: server 260 in line with 2 seeding, page 258, 0 seeding rows), so the "Paid. Your seed arrives…" text in the your-place card (`:210`) is unreachable for the buyer who just paid. A payment that becomes a refund (sold out race at the end, closed) sends no event at all: `waitingFor` never resolves and the buyer sees "Paid. Waiting for the network…", then a normal buy button, and nothing else.
- **Fix:** treat `seeding` as in line in `bump()`; broadcast `{type:'refund', wallet, signature, reason}` and show it in the pending-payment card (C3) and in "Your pieces".

### H6. Copy promises things that do not exist at launch
- **Where / what:**
  - `index.html:112` evidence 5 "The camera. The real screen, filmed, with the seed shown on it." and the Camera tab (`:39`) "The camera goes live with the first session on the real Game Boy". There is no camera or `STREAM_URL`, and the first session on the real Game Boy is the launch.
  - `index.html:70` "come back any time to watch the recording of yours." There is no recording; there is a digital replay.
  - `index.html:108` "a few parts per million off its nominal" right above a live reading of −57 ppm; and the number is the offset against the Pico's own crystal (MINT.md), not an absolute crystal error.
  - Studio "On the link cable" panel: idle mode prints synthesized `00` bytes and data mode re-times tile bytes without framing (`mint.js:494-540`), while comments and labels say "its real $00 polls" / "bytes that really crossed the link".
  - MINT.md: "Honesty is the selling point."
- **Fix:** evidence 5: "Camera: coming later. Until then each piece records its draw time and the exact tiles the Game Boy sent." Camera tab: "No camera yet." Fine print: "come back any time to replay how yours was drawn." Heartbeat: "tens of parts per million off, measured against the bridge's own crystal". Bus label: "replay of the tile data at cable speed" / hide the idle zeros or label them "idle".

### H7. Shared IPs and fast scrolling can lock buyers out
- **Where:** WebSocket cap of 6 per IP (`index.mjs:506`, closes with 1013), per-IP 600 req/min (`:418`), ticket/submit 6/min (`:423`, `:433`), Cloudflare rule 100 requests / 10 s per IP (LOGBOOK 2026-10-17). Every wall and gallery image is a request to the API (`mint.js:225`, `:626`), served `no-cache` with a `?s=` cache key (`index.mjs:402`).
- **What:** mobile carriers (CGNAT) and venue/office Wi-Fi put many buyers behind one IPv4 (verify for the launch audience). The 7th tab on that IP is closed and the page silently retries with backoff, showing "The studio is offline right now." Scrolling the gallery loads 24 images per batch with a 600 px look-ahead; a fast scroll or two people on one Wi-Fi exceed 100 requests in 10 s and Cloudflare blocks the IP for 10 s: images break, the WebSocket drops, ticket fails.
- **Fix:** serve piece images from Vercel/Arweave or with `cache-control: public, max-age=31536000, immutable` so Cloudflare caches them (they never change) and they stop counting; raise the WS cap (or count per IP+user agent) and show a clear message on close code 1013; exempt `/pieces/` from the CF rule.

### H8. A submit that times out on the buyer's side leads to a second payment
- **Where:** `index.mjs:441-443` (ticket deleted after relaying), `:435` ("Unknown or expired ticket. Start again; nothing was charged."); `mint.js:419`, `:425`.
- **What:** on a flaky phone connection the relay succeeds but the response is lost: toast "Failed to fetch". If the buyer tries again with the same ticket they are told "nothing was charged" although the first payment is on its way; if they click buy again they pay twice.
- **Fix:** keep relayed tickets as `{signature}` for 10 minutes and answer a repeat submit with the same signature (202); on the page, after any submit error, check `/api/pieces?owner` / the pending endpoint before offering a new purchase; never say "nothing was charged" on the submit path.

## Medium

### M1. Offline and connection drops show a wrong, empty studio
- **Where:** `ws.onclose` sets `snap = null` (`mint.js:310`); `renderQueue` shows `#queueEmpty` when there is no snapshot (`:172`); `renderWall` empties the wall (`:233-240`); `renderLabel(null)` text (`:106`).
- **What:** a 1-2 s WebSocket blip collapses the page from 5255 px to 2351 px (reader loses their scroll place), and shows "Nobody in line. The next commission starts right away." and "No pieces yet." With no server or with commissions closed, the label says "Nothing on the easel. The next commission starts as soon as it is paid." (`07-no-server.jpg`, `14-closed-prelaunch.jpg`, `18-ws-drop.jpg`). Reconnect itself works (1 s).
- **Fix:** keep the last snapshot on close and mark it stale ("Reconnecting… numbers from 12:04"); hide "Nobody in line" unless a snapshot says so; label text per state (closed: "Commissions open on <date>"; offline: "The Game Boy is not connected right now").

### M2. Queued pieces can be seen before the Game Boy draws them
- **Where:** `openPiece` (`mint.js:551-555`) only refuses pieces without traits; queued pieces have traits after seeding. `/api/piece` serves any piece (`index.mjs:448-451`).
- **What:** `#piece-422` for a piece still in line opens the sheet with the final picture, banner download and "Drawn: not yet", "On chain: queued" (`17-queued-piece-revealed.jpg`). It spoils the live reveal the product is built around and contradicts "watch it being drawn".
- **Fix:** open the sheet only for `drawEnd`; for others show "No. 422 is in line (place 37). Its picture appears when the Game Boy draws it." Optionally omit traits from `publicPiece` until drawn.

### M3. Gallery filters and search lose changes
- **Where:** `loadGallery` returns early while a load runs (`mint.js:607-608`); filter `change` (`:637`) and search (`:640`) call it.
- **What:** on a slow connection, choosing palette "Original" then time "night" shows 21 results with time "night" selected but 18 of them not at night (measured, `20-gallery-filter-race.jpg`). Error toast says "Retrying in a moment" (`:620`) but nothing retries. New pieces never appear until reload.
- **Fix:** abort the previous fetch (AbortController) and always load the latest filters; or queue one follow-up load; real retry with backoff; prepend newly drawn pieces on `drawn` events when sorted newest first.

### M4. The piece sheet fights the Back button
- **Where:** `history.replaceState` on open (`mint.js:582`) and on close (`:603`).
- **What:** opening a piece adds no history entry, so Back (or the phone's back gesture) leaves the page or jumps to the previous view instead of closing the sheet (measured: sheet opened from the gallery, Back went off the site). Closing drops the query string.
- **Fix:** `pushState` on open, close the sheet on `popstate`, keep `location.search` on close.

### M5. Phone layout: the buy button is below the fold, ETAs hidden, inputs zoom
- **Where:** `mint.css:183-206`, `:195`, `:212`, `:250`, `:137`.
- **What (iPhone 393x852):** the buy button starts at y=888, below the first screen (`01-demo-iphone.jpg`); the "Starts" column is hidden, so the queue on phones has no times (`04-iphone-queue.jpg`); the search input and gallery selects use 14 px, so iOS Safari zooms the page on focus (the jumpy zoom Hazy saw); the "Finished" wall is a single column 10,600 px long (page 14,600 px); 53 tap targets under 40 px (Replay/On chain links are 22 px tall); queue search placeholder is cut ("Wallet address or N").
- **Fix:** on phones put price + button above the bus panel (or a sticky bottom bar "Commission · 0.05 SOL"); keep Starts and drop Collector to a second line; 16 px inputs/selects; wall 2 columns on phones and 12 pieces with a "See all in the gallery" link; min 44 px tap height for links in cards.

### M6. Mobile wallet onboarding and wallet state
- **Where:** `connectWallet` (`mint.js:388-402`), wallet button (`:403`).
- **What:** in a normal phone browser (most visitors from X/Discord) the only help is a 7 s toast. No "Open in Phantom / Solflare / Jupiter" links, no Mobile Wallet Adapter on Android Chrome. After a reload the wallet is forgotten and "Your place" disappears until the buyer connects again. No disconnect or account switch: if the buyer changes account in the wallet, the page keeps the old address and builds payments for it. When connected with no pieces, the wallet button scrolls to a hidden section and seems dead.
- **Fix:** a mobile sheet with deep links (`https://phantom.app/ul/browse/<url>?ref=<origin>`, Solflare `https://solflare.com/ul/v1/browse/<url>`; verify Jupiter's); silent reconnect on load (`standard:connect` with `{silent:true}`, Phantom `connect({onlyIfTrusted:true})`); listen to `standard:events` change / `accountChanged`; wallet button menu with "Your pieces" and "Disconnect".

### M7. Wait times and counts disagree with each other
- **Where:** `renderPrice` (`mint.js:244-246`), `renderQueue` (`:173-181`), `renderMyPlace` (`:207-211`), `renderStudioFoot` (`:159-161`).
- **What:** the price row uses the whole line and plain minutes ("1998 ahead, about 2831 min") while the table uses hours ("in ~47 h") and the your-place card counts only pieces ahead of yours ("40 ahead of you · starts in about 46 min" next to "149 ahead, about 174 min", `03-iphone-commission.jpg`). ETAs ignore offline/paused. The studio countdown sticks at "about 0:00 to go" when a draw runs long.
- **Fix:** one formatter (min < 90 -> min, else h, else "about N days"); price row "N in line, a new piece starts in about X"; when offline/paused show "waiting for the Game Boy"; countdown "finishing up" after 0.

### M8. Heavy snapshot and images
- **Where:** `snapshot()` sends every queued piece in full (`index.mjs:358`); `perMessageDeflate` is off (ws default); pieces served at 6x (`mint.js:225`, `:626`).
- **What:** with 2000 in line the snapshot is 1.47 MB (354 KB gzipped) on every connect and reconnect, through the tunnel. Wall and gallery thumbnails load 960x864 PNGs (~21 KB) for 250 px tiles; the 1x PNG is ~2.5 KB and scales crisply with `image-rendering: pixelated`. A full gallery scroll at 2000 pieces is ~42 MB vs ~5 MB.
- **Fix:** snapshot only `{n, short, status, wallet}` for queue rows (full detail on demand); enable `perMessageDeflate` or paginate the queue via `/api/queue?offset`; use `.1x.png` for thumbnails, `.png` only in the sheet; long immutable cache headers.

### M9. Accessibility gaps
- **Where / what:**
  - Focus ring is `var(--ink)` (`mint.css:39`): 1.05:1 on the dark studio, invisible on the channel tabs (`23-focus-ring-studio.jpg`).
  - Wall and "Your pieces" images open the sheet by click only (`<img data-open>`, `mint.js:225`, `:460`): 0 of 24 keyboard reachable (the gallery uses buttons, good).
  - `--muted` #74726b on the wall is 4.17:1 (3.84:1 on #ede5d2): fine print, table headers, dt labels, placeholders are below 4.5:1.
  - No `h1` on the studio view (the only h1 is in the hidden gallery view); canvases have `aria-label` but no `role="img"`; 24 identical "Replay the draw" / "On chain" names; status line, your-place card and phase progress are not live regions (only the toast is).
  - Channel tabs: no `aria-controls`, no arrow keys.
- **Fix:** `:focus-visible { outline-color: currentColor }` or a light ring inside `.studio`; wrap images in buttons; `--muted: #66645d`; add a visually hidden h1; `role="img"` on canvases; `aria-label="Replay the draw of No. 273"`; `aria-live="polite"` on `#statusText` and `#mpLine` (throttled).

### M10. Before launch and after sell-out the page gives no direction
- **Where:** `renderStatus` (`mint.js:150`), `renderBuy` (`:256`), `renderLabel` (`:106`).
- **What:** the live site right now shows "Commissions are closed right now" with no date, no link to follow, and "Nothing on the easel. The next commission starts as soon as it is paid." Sold out shows the generic "commissions are closed right now" in the status line and "no wait".
- **Fix:** a `launchAt` / message field from the server; "Opens Oct 25, 18:00 UTC. Follow @… for the start."; sold out status "Sold out: all 2000 pieces taken. See the collection."

### M11. Failures after drawing are opaque to the collector
- **Where:** "Your pieces" status map (`mint.js:459`), refunds (`:464`).
- **What:** Arweave upload failing or a mint not landing shows "Drawn, minting" / "Minting" with no time or reason, indefinitely. "Needs a look; it will be redrawn or refunded" has no time frame. A refund for a payment made while closed before launch reads "arrived after minting ended". Minted rows have no on-chain link or asset id. Small overpayments show "0.0000 SOL".
- **Fix:** include `since` and a short public reason (`storing`, `minting, retrying`) in `publicPiece`; after 10 min: "Taking longer than usual. It is safe; it will reach your wallet." Refund reason `closed` -> "arrived while commissions were closed"; promise a refund window ("within 48 h"); add "View on chain" for minted; format SOL with up to 9 decimals.

### M12. Security headers from web/vercel.json are not served (verify)
- **Where:** `web/vercel.json` (CSP, Permissions-Policy).
- **What:** `curl -I https://www.gameboylabs.xyz/slow-horizons/` returns no `content-security-policy` and no `permissions-policy`; `slow-horizons.vercel.app` returns none either. A page that asks wallets to sign runs without its CSP.
- **Fix:** check which vercel.json the project uses since the CLI link moved to the repo root (Root Directory `web/`), redeploy, and add the headers to the gameboy-labs rewrite if proxied responses drop them.

### M13. The demo hides real states
- **Where:** `server/scripts/demo.mjs:34-38`, `:120`.
- **What:** seeding pieces carry seeds and traits (so C2 never reproduces), `/api/pieces` always returns empty (no "Your pieces", refunds or pending states), `mintOpen` is always true, and no aborts/pauses happen.
- **Fix:** mirror `publicPiece` exactly and add switches like the scratch copy used for this audit (offline, closed, sold out, abort, pause, seeding-only, collector pieces and refunds, fake ticket/submit).

## What is good

- Performance under load: 2000 in line, one new piece per second, phases every 1.5-2.5 s: no long tasks over 3 minutes, JS heap flat at ~4 MB, DOM bounded (queue paged at 10, wall capped at 24), typing in the search box responsive.
- Payment safety: the page signs only an exact two-instruction transfer of the published price to the published treasury with the expected memo (`checkPayment`), and the server re-checks the signed bytes before relaying. Payments count even without a known ticket, so closing the tab after signing cannot lose a payment.
- Server robustness: cursor-based treasury watcher, restart turns `drawing` back into `queued`, mint signature recorded before sending (idempotent), append-only payment and event logs, refunds recorded rather than lost.
- No horizontal overflow at 360, 393, 1280, 1440 or 1920 px; the desktop layout is calm and readable; the studio + wall label concept reads well.
- WebSocket reconnect works (back within 1 s) with backoff; deep links `#piece-N` and "Copy link" work; reduced motion is respected for the canvas wipe and palette fade.
- The evidence section is structured the right way (what each piece of evidence shows and does not show), and the page says plainly that the server, not a contract, runs the queue.

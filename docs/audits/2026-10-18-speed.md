# Speed audit of the drawing code (2026-10-18)

Hazy: "audit the drawing code further, we need to gain speed without breaking stuff."

Rule kept from the 10-17 speed pass: every change must give identical pixels. Checked with the golden hashes (native), WASM = native, ROM = native in PyBoy, and now also **every intermediate screen** of a drawing (new `tools/phasecheck.py`), because live viewers see those.

## Where the time goes (PyBoy, PC sampled once per frame, seeds 1 2 3 5 7 11 13 17 19 23)

Before this pass, 43,281 frames (mean 72 s per piece on these seeds):

| Share | What |
|---|---|
| 28% | 32-bit multiply and divide (library versions written in C): `__mullong` 17%, `__divslong`/`__divulong` 11% |
| 22% | screen update per phase: tile conversion `conv_row` 11%, compare `cmp_copy` 2%, VRAM copy, VBlank waits |
| 8% | 16-bit divide core `.modu16` (smooth(), cloud deck, ridge jitter `/127` and `% 5`) |
| 6% | `setT` (one call per pixel write, with bounds check, clamp and RAM bank check) |
| rest | the drawing itself (ridges 13%, sky 6%, clouds, glow, weather) |

The heaviest single call sites of the 32-bit divide were the sky's aurora/milky-way loop (gen_sky.c:91), the sun/moon ring ellipse (gen_sky.c:146) and `skyAt()`. The 32-bit multiply sat in `rnd()`, the peaks profile and the glow.

Tools: `tools/profile.py` (existing). For this audit I also used a variant that charges a helper's time to its caller, and PyBoy entry hooks on the helpers that read the real return address. A stack walk alone picks up stale words.

## Done (identical pixels)

1. **`gb/fastmath.s`**: 32-bit multiply, divide and modulo in assembly, linked in place of the library's C versions.
   - **Multiply:** bytewise, skipping zero bytes (16 x 16 operands cost four 8 x 8 products).
   - **Divide, divisor below 65536:** 16-bit remainder, one dividend byte at a time, leading zero bytes skipped.
   - **Divide, larger divisor:** only 16 steps.
   - **Correctness:** same C semantics (truncation, remainder sign). Checked by the new test ROM `gb/test/mathtest.c` + `tools/mathtest.py`: 256,000 operand pairs (random byte lengths and edge values), 0 wrong. A deliberately wrong reference is caught (256/256).
   - **Safety:** the scratch lives in WRAM, which is safe because no interrupt handler does 32-bit maths (checked: vbl, lcd, sio/rx/tx_next).
   - **Result:** seeds 1-30 mean 65.2 s -> 54.6 s (-16%). The fixed bank got 252 bytes smaller.
2. **Only convert written rows.**
   - `px_set` and `px_row` (every pixel write goes through one of them) mark the row dirty.
   - `gen_phase` converts and compares only the 8-row bands that were written since the last update.
   - The first and the last phase (P_DONE) always convert everything, so the finished picture is exact even if a write were ever missed.
   - **Result:** seeds 1-30, 54.6 s -> 50.3 s (-8%).

Together: seeds 1-30, 65.2 s -> 50.3 s (-23%). Full numbers for 1-300 are in the LOGBOOK.

## Real-console time: the link

Real-console times from the 10-18 cart test, compared with compute time in PyBoy for the same seeds: the real console takes 15-23 s longer per piece (for example volcano e8f7b1b8: 100.7 s vs 77.9 s). That is the link (8192 Hz internal clock, about 1 KB/s). `gen_phase` begins with `tx_wait()`, so drawing stops until the previous phase has gone out.

Measured with the native build (seeds 1-100, the same rows the ROM would send):

| Encoding | Link per piece |
|---|---|
| today: changed tile rows, 320 bytes each | 24.5 s |
| changed tiles only (16 bytes + index) | 22.2 s (most tiles in a changed row really change: dithered gradients) |
| changed rows, a tile equal to the tile on its left sent as a flag | about 11 s |

## Not done yet (in order of value)

1. **Link: "same as left tile" encoding.** Halves the link data (about 24 -> 11 s per piece), so most of the 15-23 s of stalls go away. Needs the ROM's `P` frame, the server parser (unit tested) and a hardware test drawing on the Mac mini before the cart swap. PyBoy can't check it, because it does not run the link against the Pico.
2. **Link: never stall.** Instead of `tx_wait()` before each phase, keep sending the newest content of each dirty row. The final frame stays exact; viewers would see slightly fewer in-between states when phases come fast. Protocol semantics change, so hardware test first.
3. **Link speed.** With the Pico driving the clock (external clock on the Game Boy) the link could run several times faster than 8192 Hz. That needs firmware and ROM work plus timing tests on hardware.
4. **16-bit divides by constants** in the ridge jitter (`/127`, `% 5`, per column) and `smooth()`: exact shift/multiply replacements, checked over the whole value range. About 3%.
5. **`conv_row`** per pixel (about 28 cycles) could lose a few cycles. About 2-3%.

**Space:** the fixed ROM bank now has about 96 bytes free and bank 1 (ridges) about 230. More assembly in bank 0 needs room made first: move non-hot code out of gen_core.c, or split a bank.

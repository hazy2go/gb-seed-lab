## 1. Critical: double processing of one payment (race between the poll and the submit loop)

**Where:** `server/src/index.mjs:70-102` (`handlePayment`), callers `index.mjs:115-118` (poll) and `index.mjs:445` (the follow-up loop after `/api/submit`, every 5 s for 60 s).

**What goes wrong:** `handlePayment` checks `state.usedSignatures[signature]` at line 71, then `await sol.inspectPayment(...)` (one RPC round trip, 100-500 ms), and only then writes `usedSignatures`. `poll()` is guarded by `polling`, but the submit loop is not, so both can be inside `handlePayment` for the same signature at once. No attacker is needed: every payment made through the page starts a submit loop. Once the transaction is finalized, the first poll tick and the next submit tick both try it. If their RPC calls overlap, both pass the check. The chance is roughly RPC latency divided by the 5 s and 8 s periods: a few percent per payment, and more with a slow RPC.

**Evidence** (`t1_race.mjs`, real handlePayment source, mocked 300 ms inspect):
```
results 1 2 | pieces 2 [ '1:SIG1', '2:SIG1' ] | payments.jsonl lines 2
maxSupply=1 -> pieces 1 refunds [{"id":1,"signature":"SIG1","wallet":"Buyer111","lamports":50000000,"reason":"sold-out","status":"due",...}] used {"SIG1":"refund:1"}
```
- Normally: two pieces, two draws and two mints for one payment, and the supply count goes up by 2.
- With one piece left: the buyer gets the piece **and** a "sold-out" refund record for the full 0.05 SOL. `usedSignatures` is overwritten to `refund:1`, so the record no longer points at the piece. If Hazy pays refunds from `refunds.csv`, the treasury loses money.

**Fix:** keep one in-flight promise per signature, and check again after the await:
```js
const inflight = new Map();
function handlePayment(sig) {
  if (!inflight.has(sig)) inflight.set(sig, handlePaymentInner(sig).finally(() => inflight.delete(sig)));
  return inflight.get(sig);
}
// inside handlePaymentInner, right after `const info = await sol.inspectPayment(...)`:
if (state.usedSignatures[signature]) return state.usedSignatures[signature];
```
Simpler alternative: the submit loop only waits and reports; it never calls `handlePayment` (the poll is at most 8 s behind). Add a reconcile check that no signature appears on two pieces, or on a piece and a refund.

## 2. High: dust spam makes 0-lamport refunds and stalls the watcher

**Where:** `solana.mjs:84-86, 108`, `index.mjs:77-86`, `index.mjs:106-126`, `index.mjs:62-68`.

**Attack:** a transaction that only carries a memo `slowhorizons:<16 hex>` and lists the treasury as a read-only account (or sends it 1 lamport) costs 5000 lamports. It appears in the treasury's `getSignaturesForAddress` with our memo, so it gets judged:
- verdict `underpaid`, so a refund record is "due" for 0 (or 1) lamports, an alert is raised, and the whole `state.json` is rewritten (fsync) for each one. That is O(n²) disk work, and `/admin/refunds.csv` fills with junk that Hazy has to triage.
- the poll handles them one after another with one `getParsedTransaction` each, and `lastPollOk` is set only when a whole poll finishes. 2000 spam transactions (0.01 SOL) at about 150 ms each make one poll take about 300 s, which is more than the 120 s limit. `mintOpen()` then returns "payment watcher behind" and `/api/ticket` refuses buyers. The attacker can keep the sale closed for very little SOL, and it also burns Helius credits.

**Evidence** (`t2_inspect.mjs`, case C):
```
C spam: treasury read-only, memo only, 0 lamports
   inspect: wallet=Buyer111… received=0 -> refund:1 pieces= refunds=[{"w":"Buyer111…","l":0,"r":"underpaid"}]
```

**Fix:** treat `received < MIN_REFUNDABLE` (for example 0.001 SOL, which is more than a refund fee) as `dust`. Log it to payments.jsonl, but create no refund record, raise no alert and skip the extra save. Update `lastPollOk` (or a progress timestamp) after each handled signature instead of once per poll. Handle up to N signatures per tick and save once per batch. Optionally prefetch with `getParsedTransactions` in batches.

## 3. High: the cold-wallet signing flow can be subverted from the hot machine

**Where:** `server/scripts/cold-tx.mjs:19-46` runs on the server (it loads the hot key and the server's RPC). `web/sign.html:41-42` shows only `signer`, `programs` and `signatures needed`.

**Scenario:** the key split exists so that a compromised Mac mini cannot take over the collection. But the incident response (`remove-delegate`) is built on that same Mac mini, and the sign page cannot tell `removeCollectionPlugin(UpdateDelegate)` apart from `updateCollectionV1 { newUpdateAuthority: attacker }`, or from an extra system transfer that drains the cold wallet. Both show as "programs: mpl-core". An attacker with the machine edits cold-tx.mjs (or its output), Hazy signs, and the attacker becomes update authority for good. That defeats the split.

**Fix:** build cold transactions on a clean machine, not the server (cold-tx only needs a public RPC and the collection address). In `sign.html`, decode the instruction: show the mpl-core instruction name and arguments. Refuse anything other than an allow-list (removeCollectionPluginV1 with UpdateDelegate, addCollectionPluginV1 with a shown address, updateCollectionV1 with only a `uri` change, and the Bubblegum updateMetadataV2 `uri`/`isMutable` changes), and refuse any System Program instruction other than the fee payer. Show `newUpdateAuthority` in red if it is present.

## 4. High: duplicate mints from a non-final "expired" or "failed" verdict

**Where:** `solana.mjs:148-154` (`mintStatus`), used at `index.mjs:310-321`.

1. "Expired" comes from two separate RPC reads: `getSignatureStatuses` (the transaction is still `processed`, so not "landed"), then `getBlockHeight('confirmed') > lastValidBlockHeight`. A transaction that lands in one of the last valid blocks can be `processed` on the first read while the height read (often served by a different node behind Helius's load balancer) is already past the limit. The caller sets `p.mintTx = null` and signs a **second** mint with a new blockhash, and both land. `sendMint` throws "block height exceeded" exactly in this late-landing case, which leads straight into this check.
2. `if (st && st.err) return 'failed'` accepts an error at `processed`. On a minority fork the same transaction can fail while it succeeds on the main fork. That is rare, but the result is again a rebuild and two mints.

**Evidence** (`t4_mint_submit.mjs`):
```
mintStatus(processed, height 1001 > lvbh 1000) = expired -> caller rebuilds and signs a second mint while the first one confirms
mintStatus(err at processed) = failed -> rebuilt on a processed-only failure
```
A duplicate gives the owner two "Slow Horizons #n" cNFTs and uses up a leaf. The tree has only 48 spare leaves (2048 vs 2000).

**Fix:** decide "expired" only when `getBlockHeight('finalized') > lastValidBlockHeight` **and** a fresh `getSignatureStatuses(..., { searchTransactionHistory: true })` made *after* that height read returns null. Treat `err` as final only when `confirmationStatus` is `confirmed` or `finalized`. Before rebuilding piece n, also check on chain that no leaf for this owner and name exists (DAS `getAssetsByOwner`, or count `numMinted` against the recorded mints). Alert on any piece with more than one landed mint signature.

## 5. Medium: wrong owner for payments that don't come from a top-level transfer; CPI memos are never seen

**Where:** `solana.mjs:87-91` (owner = source of the first **top-level** `system.transfer` to the treasury, otherwise `keys[0]`, the fee payer), `solana.mjs:108` and `reconcile.mjs:23` (only signatures whose signature-level `memo` field contains our prefix).

**Scenarios** (`t2_inspect.mjs`):
```
B smart wallet (vault pays via CPI, relayer pays fee)  -> wallet=Re1ayer… (piece minted to the relayer, not the vault)
E transferWithSeed top-level from a seeded account      -> wallet=Re1ayer… (fee payer, not the source)
```
- Squads-style vaults, fee-sponsored or gasless wallets, `transferWithSeed`, and any program that moves lamports by CPI: the piece goes to the fee payer, which can be a third-party relayer. Refunds go there too. The LOGBOOK says balance-delta accounting "covers smart wallets"; the amount does, but the owner does not.
- The signature-level `memo` field of `getSignaturesForAddress` is filled from **top-level** memo instructions only (verify on devnet; this matches agave's `extract_memos` over the message's own instructions). A vault that issues the memo inside its CPI is filtered out before `inspectPayment` runs. Neither the server nor `reconcile.mjs` sees the payment, so there is no piece and no refund record.
- Not exploitable to steal: the owner is always a signer of the payment transaction, so nobody can claim someone else's payment, and minting to a third party costs the full price.

**Fix:** parse `meta.innerInstructions` as well as top-level instructions, and accept `transfer`/`transferWithSeed` to the treasury at any depth. If the source is not a signer, or more than one source sends lamports, give the verdict `manual` (a refund record with the reason "unclear payer") instead of minting to the fee payer. In the poll and in reconcile, consider **every** treasury signature with `received > 0` that is not ours, and log or record memo-less inflows (see #8).

## 6. Medium: losing the hot key is not recoverable for the tree

**Where:** `solana.mjs:173` (`createTreeV2(..., public: false)` signed by the hot key, so the hot key is the tree creator). `mintV2` needs the tree creator or delegate (`treeCreatorOrDelegate` defaults to the payer; the devnet mint shows the placeholder, meaning "payer"). `docs/SERVER-SETUP.md:138-139` says "Losing the hot key is recoverable (the cold wallet can delegate a new one: `cold-tx.mjs add-delegate`)".

**Scenario:** the hot key is lost (disk failure without a backup) or must be rotated after a compromise. The cold wallet can make a new key the collection's UpdateDelegate, but it has no authority over the tree. Only the old hot key can `setTreeDelegate`. Minting stops until a new tree is created (about 0.077 SOL), and the code has no clean path for switching trees mid-mint. The data fingerprint does not include `MERKLE_TREE`, so nothing catches a mismatch either.

**Fix now (before launch):** have the hot key call `setTreeDelegate` to a second offline backup key (or the cold wallet), so a rotation is possible. Correct the doc. Or plan "new tree" as the recovery path and add `tree` to the store fingerprint and to each piece record.

## 7. Medium: sold-out and close races

**Where:** `index.mjs:422-431` (`/api/ticket` checks `minted() >= maxSupply` only when the ticket is issued), `index.mjs:432-447` (`/api/submit` does not call `mintOpen()`), `index.mjs:78-79`.

**Scenario:** with 1 piece left, every visitor still gets a ticket and pays, and all but one become "sold-out" refunds that Hazy repays by hand from the treasury. The buyers lose fees and Hazy has refund work. The same happens around `/admin/close`: a payment signed while the page said "open" but finalized after the close becomes a refund.

**Fix:** count reservations, meaning issued and unexpired tickets plus relayed but not yet finalized submits. Refuse new tickets once `minted() + reserved >= maxSupply`. Re-check `mintOpen()` in `/api/submit` before relaying, which is free for the buyer because nothing was sent yet. For close, compare the payment's `blockTime` with the close time and accept payments from before the close.

## 8. Medium: "every payment becomes a piece or a refund" is not true in every case

**Where:** `index.mjs:231` (`failed` after two tile mismatches: the piece counts toward supply via `minted()` at `index.mjs:34`, but no refund record and no alert beyond `mismatch`). `solana.mjs:17, 82-83` (memo must match `/slowhorizons:([0-9a-f]{16})/`, otherwise the payment is ignored silently). `solana.mjs:108` (memo-less payments are never looked at).

**Scenarios:** (a) a piece is `failed`; MINT.md:33 says "flag for a manual refund", but nothing is flagged, only `reconcile` lists it as STUCK after 6 h. (b) Someone pays by hand with `slowhorizons:ABC…` (wrong case or length): ignored, and caught only by reconcile as UNRECORDED. (c) An exchange withdrawal or a plain send of 0.05 SOL with no memo: invisible to both the server and reconcile.

**Fix:** a `failed` piece gets a refund record (reason `failed`) and stops counting toward supply, or `/admin/requeue` stays the documented path with a refund on giving up. Unrecognised memos and memo-less inflows `> dust` get a `manual` record. Reconcile should compare the treasury's total inflow against pieces plus refunds plus known non-sale transfers.

## 9. Medium: missing mainnet guards, priority fees, and wallets that modify the transaction

**Where:** `config.mjs:54-71`, `solana.mjs:51-58, 128-146`, `solana.mjs:61-71`.

- `SEED_DELAY_SLOTS` can be set to 0 or a small number on mainnet, with no check. Require `>= 32` on mainnet.
- `MINT=0` is accepted on mainnet: buyers pay and never get a mint. Refuse it on mainnet, or alert.
- `HOST` can be set to `0.0.0.0`: then `cf-connecting-ip` can be spoofed from the LAN to dodge rate limits (admin stays protected by the remoteAddress check). Require a loopback HOST on mainnet.
- No ceiling on `PRICE_SOL`. The page meta catches a typo for page buyers, but not for refunds or `received` math. Optionally require it to equal an expected value on mainnet.
- No startup check that the hot key is the collection's UpdateDelegate and the tree creator, or that `numMinted + (maxSupply - minted()) <= 2^maxDepth`.
- The `.env` parser does not strip quotes (`RPC_URL="…"` keeps the quotes).
- No priority fee on the payment or the mint (devnet mint: fee 5000, 62,772 CU, no ComputeBudget instruction). In congestion, payments expire and mints are rebuilt every ~90 s with no escalation.
- `checkSignedPayment` requires exactly 2 instructions. If a wallet adds a ComputeBudget priority-fee instruction during `signTransaction`, the server refuses a valid payment (nothing is charged, but the buyer can't buy). Which wallets do this on signTransaction rather than only on signAndSend (verify: Phantom, Solflare, Jupiter):
```
checkSignedPayment with priority fee (wallet added ComputeBudget)   -> unexpected instructions
```
**Fix:** add these guards to `checkConfig`. Add `setComputeUnitLimit(~80k)` plus `setComputeUnitPrice` (from `getRecentPrioritizationFees`, capped) to the mint and to `buildPayment`. Let `checkSignedPayment` and the page's `checkPayment` accept up to two leading ComputeBudget instructions with a capped price.

## 10. Medium: asset id and metadata availability

**Where:** `solana.mjs:155-162`, `index.mjs:312, 321`, `index.mjs:288-300`.

- `assetIdOf` gives up after 5 × 2 s and the piece is marked `minted` with `assetId: null` forever. Nothing retries it. `cold-tx.mjs piece-uri/lock-piece` then fails ("has no minted asset id"), and the page shows no asset. umi's `getTransaction` is called with no commitment, which means the RPC default (finalized), so a just-confirmed mint can be invisible for longer than 10 s (verify; the devnet piece got its id in 7.5 s).
- Minting runs right after the Arweave upload. The LOGBOOK (2026-10-17) saw arweave.net return 404 for the first minutes. Indexers and wallets fetch the JSON at mint time and can cache "no metadata".

**Fix:** compute the id without a fetch: `findLeafAssetIdPda({ merkleTree, leafIndex })`, with the leaf index from the tree's `numMinted` before the mint or from the parsed leaf. Add a backfill pass in `mintTick` for `minted && !mint.assetId`. Before minting, GET `https://arweave.net/<json id>` and the image, and wait until both return 200.

## 11. Low: outgoing treasury transactions with our memo become negative refunds

**Where:** `solana.mjs:84-92`, `index.mjs:77`. If Hazy refunds from the treasury and the wallet or tool copies a memo containing `slowhorizons:<ticket>`, the refund itself is judged as a payment:
```
D Hazy refunds from the treasury with our memo -> wallet=FJTw…(treasury) received=-50005000 -> refund:1 refunds=[{"w":"<treasury>","l":-50005000,"r":"underpaid"}]
```
**Fix:** skip transactions where the treasury is a signer, or where `received <= 0`. Tell Hazy never to put `slowhorizons:` in a refund memo.

## 12. Low: paging limits

**Where:** `solana.mjs:96-110`. After 50 pages (50,000 signatures newer than the cursor), the loop stops, but `newest` is still the newest signature, so the cursor jumps past everything older and those payments are lost silently:
```
60k sigs since cursor: newest S60000 ours [] (the memo payment at S10 is older than 50 pages: silently skipped, cursor jumps past it)
```
Unlikely for this treasury, but reachable after long downtime or deliberate spam (0.25 SOL). Also, if the RPC provider changes and the new one doesn't know the `until` signature, `until` may be ignored and the full history scanned (verify). That re-judges memo payments from before `startCursor`.
**Fix:** if the page limit is hit, process the oldest page first and move the cursor stepwise (save the oldest processed signature), or raise an alert and do not move the cursor. Store `startCursor`'s slot and ignore payments with `slot <= startSlot`.

## 13. Low: seed

**Where:** `solana.mjs:114-123`.
- Determinism checked: devnet piece 2, signature 3bsBb…, slot 512073897. Recomputed now and independently: seed 2570580157, seedSlot 512073929 (= slot+32, no skipped slot), blockhash 8KMJ…. These match the stored record (`t3_devnet.mjs`). `getBlocks` clamps at the finalized root without an error (`t5`).
- Buyer grinding: not possible. The signature is fixed at signing, and the blockhash 32 slots after the landing slot is unknown then.
- Residual risk: the leader of the first block at or after slot+32 (known in advance from the leader schedule) can change its blockhash by ordering transactions or adding filler, or can skip its slot so the next leader's hash is used. A buyer working with a large validator could aim for rare traits. That is a low incentive at 0.05 SOL; say so on the page, or mix in several later blockhashes (for example slot+32, +64, +96) to raise the cost.
- Docs: `docs/MINT.md:31` still says `seed = first 4 bytes of sha256(signature)`. The code hashes the **base58 strings** as UTF-8: `sha256(utf8(sigBase58) || utf8(blockhashBase58))`, first 4 bytes little-endian. Write this exact formula (and "first *finalized* block with slot >= payment slot + 32") into MINT.md and the metadata `properties`, so anyone can verify it.
- 32-bit seeds: the chance that two of 2000 pieces share a seed is about 0.05%.

## Verified OK

- **Value accounting cannot be inflated.** `received` is the treasury's own pre/post balance change. Lamports can leave an account only with its owner's or program's consent, the treasury can be debited only with its signature, and failed transactions are dropped (`meta.err` and the signature-level `err`). Flash-loan style borrowing has to be repaid in the same transaction, so the payer still pays. Closing accounts into the treasury counts, but those are the payer's lamports. Two times the price in one transaction gives one piece plus an `overpaid` refund of the excess (math: `excess = received - price`). Underpaid, closed and sold-out refunds are for the full `received`.
- **Nobody can claim another person's payment.** The owner is always a signer of the payment transaction: either the source of a top-level system transfer, which must sign, or the fee payer, which signs. Tickets are not authority; they only label the payment.
- **Finalized only for intake**, as the docs claim: `getSignaturesForAddress(..., 'finalized')`, `getParsedTransaction(..., 'finalized')`, and `deriveSeed` reads the finalized slot, blocks and block.
- **v0 / lookup tables:** `getParsedTransaction` uses `maxSupportedTransactionVersion: 0`; jsonParsed `accountKeys` include loaded addresses, so a treasury reached through a lookup table is still found (verify with a real v0 payment once).
- **The `/api/submit` relay cannot be used against the hot key:** the server never signs. Only the exact 2-instruction payment is relayed (price, treasury, our memo for that ticket, fee payer = sender), and v0 is refused ("unreadable"). The buyer pays the fee, and rate limits are 6/min per IP. Tests: `exact payment -> accepted`, `memo first -> not a transfer`, `other ticket memo -> wrong memo`, `v0 -> throws (caught)`.
- **The page check does not depend on the server:** `web/mint.js` checkPayment uses the page meta for treasury and price, and checks the sender and fee payer are the connected wallet and the memo is exact. A compromised server cannot redirect page payments.
- **The hot key cannot move pieces:** in the devnet mint, the leaf delegate is the owner (`parseLeafFromMintV2Transaction`: owner = delegate = XejmA…).
- **Mint crash safety:** the signature and expiry are saved before sending, and after a restart the status is checked before a rebuild. The crash-window cases are fine; the remaining hole is #4.
- **Mainnet guards present:** genesis-hash check against NETWORK; treasury != hot key; no key generated on mainnet; DEV off; https URLs; CORS origin set; STORAGE=arweave; MAX_SUPPLY <= tree leaves; the data dir is fingerprinted by network, genesis, treasury and collection. Live API: mainnet-beta, closed, treasury and price equal the page meta, CORS limited to www.gameboylabs.xyz.
- **Arweave uploads** are recorded per file before the next one, and the metadata JSON uses the final Arweave URLs and is uploaded last. Minting waits for it.
- **Admin** answers only from loopback with the token and never through the tunnel (requests carrying `cf-connecting-ip` or `x-forwarded-for` are refused). The token is compared with `timingSafeEqual`.
- **Gallery** input is bounded (facet values up to 40 characters, q up to 60, limit 1..60, offset >= 0); no injection path.
- **Hot key blast radius during the mint** (from authority-test and the LOGBOOK): it can mint fakes into the collection and edit piece metadata until the cold wallet removes it; it cannot touch the treasury. Whether the UpdateDelegate can also change the collection's name/uri or add collection plugins such as Royalties (verify on devnet). Permanent plugins can only be added at creation.
